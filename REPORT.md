# Развёртывание Qwen на CPU

Чураков Н.М. · Команда исследования технологий машинного обучения

[Репозиторий](https://github.com/AlbinoTugboat/safeboard-vllm-cpu)

## Назначение

Сервис предоставляет OpenAI-совместимый API для Qwen2.5-1.5B-Instruct BF16. Инференс выполняется на CPU через vLLM 0.32.0 в Minikube. Манифесты приложения и ConfigMap собираются Kustomize и применяются командой `kubectl --context safeboard apply -k .`.

## Архитектура

Отдельный init-контейнер скачивает модель в PVC. Ревизия `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`, размеры и SHA-256 файлов заданы в `model.lock.json`. При повторном запуске загрузчик проверяет и использует кэш. Основной контейнер монтирует PVC только для чтения и перед запуском создаёт отдельную проверенную копию файлов для vLLM.

Оба образа собираются из Dockerfile и запускаются с UID/GID 10001, read-only root filesystem и сброшенными capabilities. Базовые образы закреплены digest, прямые и транзитивные Python-зависимости — версиями и хешами.

HF token и API-ключ хранятся в разных ключах Kubernetes Secret и монтируются только в нужный контейнер. Bearer-авторизация обязательна для всех HTTP-маршрутов, кроме `GET/HEAD /health`. Журнал запросов содержит ID, операцию, статус и длительность. Содержимое запросов, ответов и исключений исключено из проверенных путей Python logging.

## Конфигурация и запуск

| Параметр | Значение |
|---|---|
| Среда | Windows 11, WSL2, Docker Desktop, Minikube, containerd |
| Kubernetes | 1.36.5; 12 логических CPU, 16 ГиБ RAM |
| Основной контейнер | requests: 8 CPU / 8 ГиБ; limits: 10 CPU / 12 ГиБ |
| Хранилище | PVC 10 ГиБ; частная копия весов около 3,1 ГБ в emptyDir до 4 ГиБ |
| CPU | OMP/MKL 7, привязка `auto` |
| Инференс | контекст 4096 токенов, KV-кэш 2 ГиБ, до 4 последовательностей и 1024 токенов в батче |

Подготовка кластера, сборка и импорт образов, создание Secret и запрос к API описаны в [README.md](README.md). Веса и значения секретов в репозиторий не входят. Параметры vLLM и CPU находятся в `k8s/serve.yaml` и `k8s/runtime.env`; изменение ConfigMap через Kustomize обновляет Pod без пересборки образа.

## Испытания

В Linux прошёл 51 тест из 51 без сети, с UID 10001 и read-only filesystem. На Windows прошли 40 тестов; 11 POSIX-проверок выполнены в Linux. Проверяются авторизация, приватность логов, защита API-ключа, целостность кэша, ветви загрузчика и расчёт метрик.

23 октября выполнен [запуск с пустым PVC](results/final-acceptance.json): первая загрузка модели, проверка SHA-256, генерация и повторный запуск из того же кэша. 24 октября проведено 20 минут смешанной нагрузки с четырьмя клиентами: 290 запросов, 0 ошибок. Вход — до 3752 токенов, выход — 64–256. Завершение активных запросов заняло ещё 17,6 с. Готовность сохранялась, OOM и прироста счётчика рестартов не было.

Максимум памяти среди 81 замера — 8,52 ГиБ при лимите 12 ГиБ, включая файловый кэш. Медиана anon первых и последних пяти замеров — 7,72 и 7,73 ГиБ. После нагрузки проверены пересоздание Pod и остановка/запуск Minikube: PVC и кэш сохранились, авторизация, генерация и приватность логов прошли проверку.

В наборе из 12 синтетических заданий исходная и выбранная конфигурации дали по 9 строгих совпадений; ранее проходившие примеры сохранились. Этот набор используется для регрессионной проверки отдельных примеров.

## Производительность

Сравнение от 23 октября выполнено в порядке A–B–B–A: A — 8 потоков без привязки, B — 7 потоков с `auto`. На каждый сценарий и вариант приходится 24 запроса с выходом 64 токена. Входы одинаковы, прогрев исключён, `cache_salt` уникален. Модель, образ и лимиты ресурсов между вариантами не менялись.

| Вход | Клиенты | TTFT B среднее / p95, с | Задержка B среднее / p95, с | Throughput A → B, токенов/с |
|---|---:|---:|---:|---:|
| 43 токена | 1 | 0,118 / 0,136 | 4,437 / 4,488 | 10,190 → 14,424 |
| 43 токена | 4 | 0,254 / 0,311 | 4,627 / 4,698 | 35,693 → 55,208 |
| 1717 токенов | 1 | 2,098 / 2,150 | 6,507 / 6,603 | 7,791 → 9,835 |
| 1717 токенов | 4 | 3,896 / 8,109 | 12,681 / 16,641 | 17,242 → 20,070 |

TTFT измеряется до первого текстового SSE-фрагмента. Throughput — сумма выходных токенов, делённая на время серии; p95 рассчитан методом ближайшего ранга.

Конфигурация B увеличила throughput на 16,4–54,7%; средний геометрический коэффициент по четырём сценариям — 1,339. Для коротких входов существенны привязка CPU и объединение запросов в батч, для длинных — обработка входа и KV-кэш. Бюджет батча 2048 не дал достаточного общего выигрыша; в конфигурации оставлено 1024. Методика и первичные данные: [results/performance-2026-10-23/README.md](results/performance-2026-10-23/README.md).

## Ограничения

Измерения относятся к одной машине с восемью физическими ядрами и SMT. p95 по 24 запросам и 20 минут закрытой нагрузки с четырьмя клиентами недостаточны для оценки длительной работы под произвольной входящей нагрузкой.

При первоначальном восстановлении кластера один старт inference завершился с кодом 1; повторный запуск восстановил готовность. Причина не установлена: логи предыдущего контейнера были недоступны. При контрольной остановке и запуске после нагрузки сбой не повторился. Прерванная попытка нагрузки от 23 октября исключена из итоговых измерений.

Доступ организован через loopback port-forward. Внешняя публикация требует TLS и ограничений доступа и нагрузки. Форматтер и Python exception hooks не фильтруют произвольный native/raw stdout. Отдельная копия модели увеличивает время старта и расход файлового кэша памяти.

Остаются замечания сканера к setuptools, его встроенным jaraco.context/wheel и пакетам ОС. Обновление Python-зависимостей требует совместимого набора для CPU vLLM; штатный offline inference не вызывает связанные сценарии установки и распаковки архивов. Подробности — в [отчёте по безопасности](results/security-fixes.md). Изменяемые репозитории apt ограничивают побитовую воспроизводимость сборки.
