## Назначение и результат

Локальный сервис предоставляет OpenAI-совместимый API для Qwen2.5-1.5B-Instruct BF16. Инференс выполняется на CPU через vLLM 0.32.0 в Minikube. Развёртывание описано манифестами Kubernetes и Kustomize; отдельный init-контейнер загружает модель в постоянное хранилище.

На тестовой машине выбраны семь CPU-потоков с автоматической привязкой. В сравнении с восемью потоками без привязки throughput вырос на 16,4–54,7% в зависимости от сценария. Двадцатиминутная проверка с четырьмя клиентами завершила 290 запросов без ошибок, OOM и прироста счётчика рестартов. Методика, команды запуска и ограничения приведены ниже.

## Устройство сервиса

### Контейнеры и конфигурация

Основной образ `safeboard-vllm:0.32.0` собирается многоэтапным Dockerfile из CPU-wheel vLLM и CPU-сборки PyTorch. Для загрузки используется отдельный образ `safeboard-downloader:1.3` с Hugging Face Hub. Базовые образы Python и uv, а также Dockerfile frontend закреплены digest. Прямые и транзитивные Python-зависимости закреплены версиями и хешами; установка выполняется через uv с `--require-hashes` и `--no-build`. Базовые pip и ensurepip удалены из runtime-образов.

Оба контейнера запускаются с UID/GID 10001, read-only root filesystem, сброшенными Linux capabilities и `seccompProfile: RuntimeDefault`. Повышение привилегий и автоматическое монтирование service account token отключены. Временные данные размещаются в отдельных emptyDir.

| Файлы | Назначение |
|---|---|
| Dockerfile и Dockerfile.downloader | сборка inference и загрузчика |
| kustomization.yaml и k8s/ | Namespace, Deployment, Service, PVC и генерация ConfigMap |
| k8s/serve.yaml | параметры vLLM |
| k8s/runtime.env | переменные CPU и пути конфигурации |
| model.lock.json | ревизия, размеры и SHA-256 файлов модели |
| app/ | загрузка и проверка модели, запуск, авторизация и журналирование |
| scripts/ и tests/ | клиент, создание Secret, проверки и нагрузочные измерения |
| results/ | результаты испытаний и измерений |

### Загрузка и целостность модели

Init-контейнер проверяет существующий кэш до обращения к Hugging Face. Корректный кэш используется без сетевого скачивания. Новые файлы загружаются в каталог `.partial`; после проверки каталог атомарно переименовывается. Незавершённая загрузка сохраняется для следующей попытки, файловая блокировка исключает одновременную запись в один кэш.

В каталоге модели допускаются только файлы manifest и служебное дерево `.cache/huggingface` без symlink. Дополнительные веса, index, шаблоны и symlink отклоняются. Повреждённый готовый кэш вызывает отказ `existing_cache_invalid` до сетевого обращения и автоматически не перезаписывается.

Основной контейнер монтирует PVC только для чтения. Перед запуском vLLM он копирует manifest-файлы в `/verified-model/model`, одновременно проверяя размер и SHA-256 копируемых байтов. Этот emptyDir доступен только inference-контейнеру. Движок работает с отдельной копией в offline-режиме: `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `trust-remote-code=false`.

При каждом старте inference предыдущая частная копия заменяется. Это требует около 3,1 ГБ дополнительного диска, локального копирования и проверки SHA-256; сетевого скачивания при корректном PVC нет. Файловый кэш копии учитывается в памяти контейнера. Изменение общего PVC после копирования не меняет файлы, которые читает движок. Писатель с доступом к PVC всё ещё может повредить кэш и сорвать следующий запуск; доступ к inference-контейнеру или его конфигурации находится за этой границей защиты.

### Авторизация и журналирование

HF token и API-ключ находятся в разных ключах Secret `vllm-tokens`. Downloader получает только `hf-token`, inference — только `api-token`. Значения не передаются в аргументах процессов. Bearer-авторизация обязательна для всех HTTP-маршрутов, включая `/v1/models`, `/tokenize` и `/metrics`; исключение — `GET/HEAD /health` для Kubernetes probes. WebSocket-соединения закрываются.

ASGI middleware сохраняет случайный request ID, операцию, HTTP-статус и длительность. Для авторизованных запросов middleware не читает тело и не буферизует поток ответа. При раннем отказе 401 короткое тело отбрасывается без логирования с пределом 32 КиБ и 0,25 с. Большие и медленные тела не вычитываются без ограничения.

Логирование запросов и генераций vLLM отключено принудительными аргументами запуска. MetadataFormatter исключает текст сообщений, аргументы logging и содержимое исключений; сохраняются уровень, модуль, тип ошибки и место в коде. Python exception hooks также очищают warnings, необработанные traceback и ошибки cleanup. Произвольный native/raw stdout этим механизмом не фильтруется.

Клиент не использует системные HTTP-прокси и запрещает redirects, в том числе на тот же адрес. API-ключ не пересылается по адресу из Location. Незашифрованный HTTP разрешён только для loopback; внешний endpoint должен использовать HTTPS. URL с credentials, query или fragment отклоняются до сетевого запроса.

## Развёртывание

### Подготовка среды

На машине должны быть установлены Docker Desktop с WSL2, Minikube, kubectl и Python 3.12. Для сборки образов и первой загрузки модели требуется доступ к сети. Отдельная установка Kustomize не нужна: используется поддержка в kubectl. Команды ниже выполняются в PowerShell из корня репозитория.

```powershell
docker desktop start
minikube start -p safeboard --driver=docker `
  --container-runtime=containerd --cpus=12 --memory=16384 `
  --kubernetes-version=v1.36.5 --listen-address=127.0.0.1
```

### Сборка и импорт образов

```powershell
docker build -t safeboard-vllm:0.32.0 -f Dockerfile .
docker build -t safeboard-downloader:1.3 -f Dockerfile.downloader .
minikube image load safeboard-vllm:0.32.0 `
  safeboard-downloader:1.3 -p safeboard
```

### Создание Secret и запуск

```powershell
kubectl --context safeboard apply -f k8s/namespace.yaml
python scripts/create_secret.py --context safeboard
kubectl --context safeboard apply -k .
kubectl --context safeboard -n safeboard-llm `
  rollout status deployment/vllm --timeout=15m
```

Утилита создания Secret генерирует API-ключ, передаёт его kubectl через stdin и сохраняет существующий Secret при повторном вызове. Для публичной Qwen токен Hugging Face не требуется: ключ `hf-token` остаётся пустым. Если используется закрытая модель, утилита получает токен из переменной окружения `HF_TOKEN`. Веса и значения секретов в репозиторий не входят.

Первая загрузка скачивает около 3,1 ГБ. До её завершения и подготовки движка Pod может оставаться неготовым. Состояние загрузки проверяется по логам init-контейнера; команды диагностики приведены в разделе эксплуатации.

### Запрос к API

В отдельном терминале оставить работающим port-forward:

```powershell
kubectl --context safeboard -n safeboard-llm `
  port-forward --address=127.0.0.1 service/vllm 8000:8000
```

В основном терминале выполнить запрос:

```powershell
python scripts/client.py "Объясни, что такое контейнер."
```

Адрес — `http://127.0.0.1:8000/v1/chat/completions`, имя модели — `safeboard-qwen`. Клиент читает API-ключ из Secret в память. Для работы вне локального кластера ключ можно передать через `LLM_API_TOKEN`.

### Повторный запуск и обновление

Остановка профиля сохраняет PVC и состояние Kubernetes. После остановки достаточно запустить Docker и существующий профиль:

```powershell
docker desktop start
minikube start -p safeboard
```

Параметры vLLM меняются в `k8s/serve.yaml`, переменные CPU — в `k8s/runtime.env`. Применение изменений:

```powershell
kubectl --context safeboard apply -k .
kubectl --context safeboard -n safeboard-llm `
  rollout status deployment/vllm --timeout=15m
```

Kustomize меняет хеш имени ConfigMap, что обновляет Pod без пересборки образа. После изменения кода нужно пересобрать соответствующий образ и повторить его импорт в Minikube. Если тег сохранён, перезапуск выполняется явно:

```powershell
kubectl --context safeboard -n safeboard-llm `
  rollout restart deployment/vllm
kubectl --context safeboard -n safeboard-llm `
  rollout status deployment/vllm --timeout=15m
```

## Эксплуатация

### Состояние и логи

```powershell
kubectl --context safeboard -n safeboard-llm get pods,pvc
kubectl --context safeboard -n safeboard-llm `
  logs deployment/vllm -c download-model
kubectl --context safeboard -n safeboard-llm `
  logs deployment/vllm -c inference
minikube stop -p safeboard
```

Для проверки готовности используется `/health`. Остановка Minikube сохраняет данные; удаление PVC, namespace или профиля может удалить хранилище модели.

### Ошибки DNS

На тестовой машине синтетический DNS-адрес Docker Desktop был недоступен из обычной сети Pod. Для локального одноузлового профиля CoreDNS переведён в сеть узла с `dnsPolicy: Default`. Если init-контейнер не разрешает имена Hugging Face:

```powershell
.\scripts\repair_minikube_dns.ps1
kubectl --context safeboard -n safeboard-llm `
  rollout restart deployment/vllm
```

Утилита меняет CoreDNS в профиле `safeboard`. В кластере с работающим DNS эта настройка не требуется.

### Восстановление повреждённого кэша

Готовый кэш с неверными хешами автоматически не перезаписывается. Для восстановления администратор останавливает Deployment, подключает PVC к служебному Pod с UID/GID 10001 и переносит каталог `Qwen--Qwen2.5-1.5B-Instruct@<revision>` в карантин. После возобновления Deployment загрузчик создаёт модель заново через `.partial`.

Перед повторной загрузкой требуется свободное место для повреждённой и новой копий. Удалять PVC целиком для этой процедуры не требуется.

## Измерения производительности

### Методика сравнения

23 октября предварительно проверены конфигурации 8 потоков без привязки, 7 с `auto`, ручная привязка шести физических ядер и бюджет батча 2048. Подтверждающая серия использовала порядок A–B–B–A: A — 8 потоков с `nobind`, B — 7 потоков с `auto`. Каждый проход запускался в новом Pod и включал по 12 запросов в четырёх сценариях: короткий или длинный вход, один или четыре клиента. Итого — 192 запроса, по 24 на сценарий и конфигурацию, по 64 выходных токена.

Входы одинаковы между вариантами; уникальный `cache_salt` исключает повторное использование префикса. Прогрев исключён. Модель BF16, образ, контекст и лимиты ресурсов между A и B не менялись. До и после каждого прохода сохранены UID Pod, image ID, хеши конфигурации и привязка endpoint к audit ID; Pod и настройки совпали.

TTFT — время до первого непустого текстового SSE-фрагмента на клиенте. Полная задержка измеряется до завершения ответа. Throughput — сумма выходных токенов, делённая на суммарное время измеряемых серий. p95 рассчитан методом ближайшего ранга.

Данные от 21 октября в results/benchmark.json, results/environment.json и results/performance/ относятся к прежним настройкам и в эту серию не включены.

### Нагрузочная проверка

24 октября выполнено 20 минут непрерывной закрытой нагрузки с четырьмя клиентами: каждый отправляет следующий запрос после завершения предыдущего. После окна новые запросы не отправлялись, активные завершились. Полное время с их завершением — 1217,6 с.

Пять чередующихся сценариев включали короткий вход с выходом 64 или 256 токенов, длинный с выходом 64 или 128 и вход до 3752 токенов с выходом 128. Каждая генерация использовала отдельный `cache_salt`. Содержимое запросов и ответов в результат не записывалось. Ресурсы и готовность проверялись примерно каждые 15 с; промежуточные метаданные сохранялись раз в минуту.

### Контроль качества ответов

На 12 синтетических заданиях исходная и выбранная конфигурации дали по 9 строгих совпадений. Все ранее проходившие примеры сохранились. Набор используется для регрессионной проверки отдельных примеров и не является оценкой общей точности модели.

### Повторение измерений

При работающем port-forward измерить текущую конфигурацию можно следующими командами:

```powershell
python scripts/benchmark_decode.py --requests 24 `
  --output-tokens 64 --prompts short long --concurrency 1 4 `
  --kube-context safeboard --output results/current-benchmark.json
python scripts/soak_test.py --duration-seconds 1200 `
  --concurrency 4 --kube-context safeboard `
  --output results/current-soak.json
```

Benchmark проверяет соответствие локальной конфигурации Pod и привязывает endpoint к его audit log. Изменение Pod или настроек во время измерения приводит к отказу проверки. Результаты повторного запуска сохраняются отдельно от исторических данных.

## Ограничения и открытые вопросы

Результаты относятся к одной машине с восемью физическими ядрами и SMT. Чередование A–B–B–A уменьшает влияние порядка прогонов, но не устраняет внешние факторы. p95 по 24 запросам и 20 минут закрытой нагрузки недостаточны для оценки длительной работы под произвольной интенсивностью запросов или медленных утечек памяти.

При первоначальном восстановлении кластера до нагрузки один старт inference завершился с кодом 1; повторный запуск восстановил готовность. Причина не установлена: логи предыдущего контейнера были недоступны. Событие предшествовало измеряемому окну; в нагрузке проверялось отсутствие прироста исходного счётчика рестартов. При контрольной остановке и запуске после нагрузки сбой не повторился.

Сервис рассчитан на локальный доступ через loopback port-forward. Внешняя публикация требует TLS и ограничений доступа и нагрузки. Публичный pentest и разрушительные CVE/DoS-проверки не проводились. Python logging и exception hooks не фильтруют произвольный native/raw stdout.

В inference остаётся `setuptools==78.1.1` и его встроенные jaraco.context/wheel: CPU-wheel vLLM 0.32.0 требует этот pin. После удаления базового pip сканирование от 23 октября не выявило Python CVE в downloader; в inference осталось три совпадения setuptools/vendor. Также сохраняются совпадения по пакетам ОС, в том числе заголовкам ядра и build tooling. Эти результаты не скрыты ignorelist и не означают доказанную удалённую эксплуатацию API.

Обновление Python-зависимостей требует совместимого набора для CPU vLLM. Штатный offline inference не вызывает связанные сценарии установки и распаковки архивов, однако это не устраняет сами замечания сканера. Репозитории apt остаются изменяемым входом сборки, поэтому побитовая воспроизводимость не заявляется.
