# Чураков Н.М. Команда исследования технологий машинного обучения

## Результат

Подготовлена система инференса Qwen2.5-1.5B-Instruct на CPU через vLLM 0.32.0 в Minikube. Выполнены основные требования и три дополнительных задания: Kustomize, отдельный контейнер первичной загрузки и нагрузочное тестирование.

Решение включает исходный код, два Dockerfile, зависимости с версиями и хешами, Kubernetes-манифесты, инструкции запуска, тесты и результаты проверок. Веса модели и секреты в репозиторий не входят. Модель автоматически загружается при первом запуске.

## Соответствие заданию

| Требование | Реализация и подтверждение |
|---|---|
| Kubernetes или Minikube | Minikube с Docker-драйвером, containerd и Kubernetes 1.36.5; манифесты в `k8s/` |
| Instruct-модель, только CPU, vLLM ≥ 0.27.0 | Qwen2.5-1.5B-Instruct BF16, vLLM 0.32.0; CPU-колёса PyTorch, проверка отсутствия CUDA при сборке, GPU-ресурсы не запрашиваются |
| Собственный образ, непривилегированный пользователь | Многоэтапный `Dockerfile`, UID/GID 10001; read-only root filesystem, запрет повышения привилегий, сброшенные capabilities |
| Фиксация всех Python-зависимостей | `requirements.txt` и `requirements-downloader.txt`: прямые и транзитивные зависимости с точными версиями и хешами; установка без сборки из исходников |
| Приватность логов и регистрация обращений | Форматтер метаданных, ASGI middleware, Python exception hooks; журнал содержит ID, статус и длительность, без prompt и ответа; проверены успешные и ошибочные запросы |
| Первое скачивание и повторное использование PVC | InitContainer скачивает точную ревизию, проверяет SHA-256 и публикует готовый каталог; повторный запуск использует локальный проверенный кэш |
| HF token и Bearer token через Secret | `scripts/create_secret.py`; каждому контейнеру передаётся только нужный ключ. Для публичной Qwen HF token пустой; Bearer token генерируется локально |
| Параметры через ConfigMap | `k8s/serve.yaml` и `k8s/runtime.env`; Kustomize меняет имя ConfigMap при изменении содержимого, вызывая обновление Pod |
| Инструкция запуска | [README.md](README.md), автоматическое развёртывание через `scripts/deploy.ps1`, ручные команды и клиент |

Веса закреплены на commit `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`. В [model.lock.json](model.lock.json) заданы размеры и SHA-256 семи файлов. После проверки общий PVC копируется в отдельное хранилище основного контейнера: vLLM читает только проверенную частную копию.

## Дополнительные задания

1. **Kustomize:** `kubectl --context safeboard apply -k .`; ConfigMap создаются из файлов проекта.
2. **Отдельная загрузка:** непривилегированный initContainer из `Dockerfile.downloader` содержит Hugging Face Hub без vLLM/PyTorch. Основной контейнер работает в offline-режиме.
3. **Нагрузочное тестирование:** собственный streaming-клиент измеряет TTFT, полную задержку и суммарный throughput для коротких и длинных запросов с параллелизмом 1 и 4. Команда, таблица и анализ настроек приведены в README; исходные метрики — [results/benchmark.json](results/benchmark.json).

## Производительность

Измерения выполнены 21 октября 2026 года: восемь запросов на сценарий, 32 выходных токена, отдельный прогрев. TTFT и задержка в таблице — средние значения.

| Вход | Параллелизм | TTFT, с | Полная задержка, с | Выходных токенов/с |
|---|---:|---:|---:|---:|
| Короткий, 68 токенов | 1 | 1,107 | 3,204 | 9,987 |
| Короткий, 68 токенов | 4 | 1,077 | 3,866 | 32,988 |
| Длинный, 1745 токенов | 1 | 2,159 | 5,168 | 6,192 |
| Длинный, 1745 токенов | 4 | 4,417 | 11,304 | 11,177 |

Для потока коротких запросов полезно подбирать размер батча, число активных последовательностей и число CPU-потоков. Для длинных контекстов ограничивающими факторами становятся prefill и KV-кэш; увеличение throughput нужно оценивать вместе с TTFT и расходом памяти. Более подробное обсуждение и p95 приведены в README.

После исправлений безопасности настройки генерации сохранены: BF16, OMP/MKL 8, `nobind`, контекст 4096, KV-кэш 2 ГиБ. Приведённые измерения относятся к образу от 21 октября; повторный benchmark финального образа не проводился. Дополнительные эксперименты сохранены отдельно в [results/performance/README.md](results/performance/README.md), их настройки в рабочее решение не перенесены.

## Проверки и безопасность

- 48 из 48 тестов проходят в Linux-контейнере без сети, с непривилегированным пользователем и read-only filesystem. На Windows проходят 37 тестов, 11 POSIX-проверок выполняются в Linux.
- Оба Dockerfile успешно собираются; Kubernetes-конфигурация успешно формируется через Kustomize.
- На реальной модели проверены Bearer-аутентификация, генерация, отклонение ошибочного ввода, регистрация обращений и отсутствие проверяемых приватных данных в логах.
- 23 октября выполнен контрольный запуск финальных образов в новом профиле Minikube с пустым PVC. Модель реально скачалась и прошла SHA-256; после пересоздания Pod использовался тот же PVC без повторного скачивания. До и после пересоздания прошли API/privacy-проверки; автоматических рестартов контейнеров в ходе проверки не было. Сводка — [final-acceptance.json](results/final-acceptance.json).
- Проверены работа с кэшем при `HF_HUB_OFFLINE=1` и повторный старт inference в том же Pod с заменой частной копии модели.
- Выполнен аудит приложения, платформы и зависимостей. Исправлены маршрутизация клиентского токена через системный proxy и возможность влияния лишних файлов/изменений общего PVC на загрузку модели. Из рабочих образов удалён старый базовый pip.
- Перед публикацией выполнено сканирование каталога решения на секреты; обнаружений нет.

Подробные результаты: [tests.json](results/tests.json), [security-fixes.json](results/security-fixes.json), [отчёт об исправлениях](results/security-fixes.md).

## Ограничения

Решение рассчитано на локальный однопользовательский доступ через loopback port-forward. Для внешней публикации понадобятся отдельное проектирование доступа, TLS, ограничения нагрузки и наблюдаемость. Клиент уже требует HTTPS для внешних адресов.

В inference остаются замечания сканера к setuptools и его встроенным jaraco.context/wheel, а также к пакетам ОС. Текущий CPU-wheel vLLM требует точную версию setuptools; совместимое обновление этого набора выделено как дальнейшая работа. Связанные сценарии распаковки архивов и установки пакетов не вызываются штатным offline inference. Полное отсутствие уязвимостей не заявляется.

Механизм приватности покрывает проверенные Python logging/exception-пути; произвольный native/raw stdout им не фильтруется. Нагрузочные измерения имеют небольшую выборку и не заменяют длительный стресс-тест.

Воспроизводимость обеспечивается фиксацией Python-зависимостей, базовых образов и ревизии модели. Репозитории apt остаются изменяемыми; побитовая воспроизводимость полной сборки не заявляется. Для проверки сборок разрешён Docker build cache.

Кластер использует 12 логических CPU и 16 ГиБ RAM, основной контейнер — лимит 10 CPU / 12 ГиБ. Требуются PVC 10 ГиБ, около 3,1 ГБ для частной копии модели, место для образов и временных файлов. Копирование увеличивает время старта и использование файлового кэша памяти.

## Запуск проверяющим

1. Установить Docker Desktop с Linux-контейнерами, Minikube, kubectl и Python 3.12; выделить ресурсы согласно README.
2. В PowerShell из корня проекта выполнить `./scripts/deploy.ps1`.
3. В отдельном терминале выполнить `kubectl --context safeboard -n safeboard-llm port-forward --address=127.0.0.1 service/vllm 8000:8000`.
4. Выполнить `python scripts/client.py "Объясни, что такое контейнер, двумя предложениями."`.
5. Для проверки доступа и приватности выполнить `python scripts/verify_endpoint.py --context safeboard`.
6. После работы выполнить `minikube stop -p safeboard`: модель и состояние сохранятся.

Если локальный DNS Docker Desktop мешает загрузке, в README описан отдельный диагностированный обход для Minikube. Ключи доступа создаются на машине проверяющего; готовых секретов в комплекте нет.
