# Инференс Qwen на CPU в Minikube

Проект запускает Qwen2.5-1.5B-Instruct через vLLM 0.32.0 в локальном Kubernetes. Основной контейнер и отдельный контейнер загрузки работают с UID 10001. Веса сохраняются в PVC и проверяются по SHA-256. Параметры инференса вынесены в ConfigMap, токены — в Secret.

Автор: **Чураков Н.М.** Команда исследования технологий машинного обучения. [Итоговый технический отчёт](REPORT.md) содержит соответствие требованиям, результаты и ограничения. Репозиторий: [AlbinoTugboat/safeboard-vllm-cpu](https://github.com/AlbinoTugboat/safeboard-vllm-cpu).

## Устройство проекта

```text
Hugging Face → initContainer → PVC → проверенная частная копия → vLLM на CPU
                                                                  ↑
Клиент → локальный port-forward → Bearer auth → HTTP API ────────────┘
                                                  ↓
                                    журнал метаданных запросов
```

- `Dockerfile` — многоэтапная сборка основного образа из CPU-wheel vLLM.
- `Dockerfile.downloader` — отдельный лёгкий образ с Hugging Face Hub.
- `requirements.txt`, `requirements-downloader.txt` — полные графы зависимостей с версиями и хешами.
- `model.lock.json` — точный commit модели, размеры и SHA-256 всех используемых файлов.
- `app/` — загрузка, проверка кэша, запуск, авторизация и кастомное логирование.
- `k8s/` и `kustomization.yaml` — манифесты и ConfigMap.
- `scripts/` — развёртывание, клиент, проверки и нагрузочный тест.
- `tests/` — проверки приватности, авторизации и целостности кэша.
- `results/` — результаты реальных проверок и измерений.

## Среда

Проверяемая конфигурация: Windows 11 → WSL2 → Docker Desktop → Minikube с Docker-драйвером и containerd. Требуются Docker, Minikube, kubectl, Python 3.12 и uv. Отдельный Kustomize устанавливать не требуется.

Кластер `safeboard` имеет квоты 12 логических CPU и 16 ГиБ памяти. WSL2 ограничена 20 ГБ. У приложения запрос 8 CPU / 8 ГиБ и лимит 10 CPU / 12 ГиБ; KV-кэш задан отдельно — 2 ГиБ. У init-контейнера лимит 2 CPU / 1 ГиБ. GPU-ресурсы и устройства не подключаются, PyTorch установлен в CPU-варианте.

Основной контейнер использует отдельный дисковый `emptyDir` до 4 ГиБ для проверенной копии весов. Для текущей модели нужно около 3,1 ГБ дополнительного временного диска. Копия создаётся и проверяется при каждом старте inference; настройки генерации сохранены.

Базовые образы Python и uv закреплены digest. Python-зависимости устанавливаются с `--require-hashes` и `--no-build`; CPU-колёса PyTorch выбираются явно. Версия модели: `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`.

Dockerfile frontend также закреплён digest. Из runtime-образов удалены базовый pip и ensurepip; сборка использует uv. Зависимости setuptools внутри venv сохранены по точному требованию CPU vLLM: их обновление требует совместимого upstream-перехода. Статус известных рисков и проверок описан в [results/security-fixes.md](results/security-fixes.md).

## Развёртывание

Открой PowerShell в корне проекта. Запусти Docker Desktop, затем:

```powershell
docker desktop start
.\scripts\deploy.ps1
```

Скрипт создаёт или запускает профиль `safeboard`, собирает оба образа, импортирует их в Minikube, создаёт Secret и применяет Kustomize. Все шаги, включая создание Secret, явно используют context `safeboard`; переменная `KUBE_CONTEXT` не меняет цель развёртывания. Первый запуск скачивает около 3,1 ГБ весов. Для публичной Qwen Hugging Face token не нужен; ключ `hf-token` в Secret остаётся пустым.

Если нужна gated-модель, токен передаётся скрипту через переменную окружения `HF_TOKEN` при первом создании Secret. Сам токен не печатается и не передаётся в аргументах процессов. Скрипт сохраняет существующий Secret при повторном запуске.

Те же действия вручную:

```powershell
minikube start -p safeboard --driver=docker --container-runtime=containerd --cpus=12 --memory=16384 --kubernetes-version=v1.36.5 --listen-address=127.0.0.1
docker build -t safeboard-vllm:0.32.0 -f Dockerfile .
docker build -t safeboard-downloader:1.3 -f Dockerfile.downloader .
minikube image load safeboard-vllm:0.32.0 safeboard-downloader:1.3 -p safeboard
kubectl --context safeboard apply -f k8s/namespace.yaml
python scripts/create_secret.py --context safeboard
kubectl --context safeboard apply -k .
kubectl --context safeboard -n safeboard-llm rollout status deployment/vllm --timeout=15m
```

На тестовой машине обнаружена особенность DNS Docker Desktop: синтетический адрес DNS обрабатывается правилами OUTPUT узла и недоступен обычному сетевому трафику CoreDNS Pod. Для локального одноузлового профиля CoreDNS переведён в сеть узла с `dnsPolicy: Default`. Проверено получение HTTP 200 от Hugging Face из Pod. Если в аналогичной среде init-контейнер сообщает сетевые ошибки:

```powershell
.\scripts\repair_minikube_dns.ps1
kubectl --context safeboard -n safeboard-llm rollout restart deployment/vllm
```

Эта настройка относится к локальной инфраструктуре Minikube; в обычном Kubernetes с исправным DNS она не нужна.

## Запрос к модели

В отдельном терминале оставь работающим проброс порта:

```powershell
kubectl --context safeboard -n safeboard-llm port-forward --address=127.0.0.1 service/vllm 8000:8000
```

В основном терминале:

```powershell
python scripts/client.py "Объясни, что такое контейнер, двумя предложениями."
```

Клиент читает API-токен из Secret в память. Для клиента вне локального Kubernetes можно передать `LLM_API_TOKEN` через окружение. API совместим с форматом OpenAI: `POST /v1/chat/completions`, модель `safeboard-qwen`. Клиент запрещает HTTP redirects, включая перенаправления на тот же адрес: ответ 3xx завершает запрос ошибкой, Bearer token не отправляется по адресу из `Location`.

Клиент не использует системные HTTP proxy. Незашифрованный HTTP разрешён только для loopback; внешнему endpoint требуется HTTPS. Credentials в URL, query и fragment в базовом адресе отвергаются до запроса.

В Pod каждый контейнер получает только нужный ключ Secret: downloader — `hf-token`, inference — `api-token`. Значения не передаются аргументами процессов.

Все HTTP-маршруты, кроме `GET /health` и `HEAD /health`, требуют Bearer token. Это распространяется также на альтернативные маршруты вроде `/invocations`, `/tokenize` и `/metrics`. WebSocket-соединения закрываются. Проверки Kubernetes используют `/health`.

## Кэш и конфигурация

Init-контейнер сначала проверяет размеры и SHA-256 локальных файлов. Если кэш корректен, он завершается до импорта Hugging Face Hub. Новые файлы скачиваются в каталог `.partial`; после проверки каталог атомарно переименовывается. Незавершённая загрузка сохраняется для повторной попытки. Блокировка файла исключает одновременную загрузку в один кэш.

В каталоге модели разрешены только файлы manifest и служебное дерево `.cache/huggingface` без symlink. Незаявленные index, веса, шаблоны и другие файлы приводят к отказу; symlink каталогов также отвергаются. Некорректный `.partial` отклоняется до импорта Hub. Служебные metadata не передаются движку.

Основной контейнер монтирует PVC только для чтения и запускается с `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`. Путь включает полный commit модели. Повреждённые файлы не передаются движку; при повреждённом готовом кэше init-контейнер сразу отказывает с причиной `existing_cache_invalid`, до импорта HF Hub и любых сетевых вызовов.

Перед запуском vLLM launcher копирует ровно manifest-файлы в `/verified-model/model`, одновременно проверяя размер и SHA-256 копируемых байтов. Этот отдельный `emptyDir` доступен только inference-контейнеру. vLLM читает собственную копию; последующая подмена общего PVC её не меняет. При рестарте контейнера предыдущая частная копия заменяется, поэтому копии не накапливаются. Это добавляет локальное копирование при старте; повторного сетевого скачивания нет. Писатель с доступом к самому inference-контейнеру остаётся за этой границей защиты.

Для восстановления останови Deployment, подключи PVC к служебному Pod с UID/GID 10001 и перенеси повреждённый каталог `Qwen--Qwen2.5-1.5B-Instruct@<revision>` в отдельный карантинный каталог. Затем возобнови Deployment: отсутствие финального каталога разрешит проверенную загрузку через `.partial`. Повреждённый финальный каталог автоматически не перезаписывается. Перед повторной загрузкой проверь свободное место для обеих копий; PVC целиком удалять не требуется.

Хеш `source_manifest_sha256` в `results/environment.json` вычисляется по каноническому JSON: UTF-8, сортировка ключей, разделители `,` и `:`, `ensure_ascii=True`, без NaN. Формат обозначен `sha256-canonical-json-v1`; переводы строк и отступы исходного файла на этот хеш не влияют.

Параметры изменяются в `k8s/serve.yaml`, переменные CPU — в `k8s/runtime.env`. После изменения:

```powershell
kubectl --context safeboard apply -k .
```

Kustomize меняет хеш имени ConfigMap, что запускает обновление Pod. Пересборка образа для изменения этих настроек не нужна. После изменения кода и повторной сборки образа требуется `kubectl rollout restart deployment/vllm -n safeboard-llm --context safeboard`; скрипт развёртывания делает это сам.

`enableServiceLinks: false` предотвращает конфликт автоматически создаваемой Kubernetes переменной `VLLM_PORT` с одноимённым параметром vLLM.

## Приватность логов

`MetadataFormatter` не сериализует текст стандартных сообщений, аргументы логирования и содержимое исключений. Для диагностики сохраняются уровень, имя модуля, тип ошибки и место в коде. Обращения регистрирует ASGI middleware: случайный `request_id`, тип операции, HTTP-статус и длительность. Для авторизованных запросов middleware не читает тело и не буферизует поток ответа. Перед 401 короткое тело запроса отбрасывается без логирования, с пределом 32 КиБ и 0,25 с, чтобы уменьшить сбросы TCP при раннем отказе; большие и медленные тела не вычитываются без ограничения.

Логирование запросов и генераций vLLM отключено отдельными принудительными аргументами запуска. `sitecustomize.py` дополнительно очищает прямые Python warnings и необработанные traceback, в том числе из дочерних процессов, деструкторов и atexit. Это проверка конкретных logging/hook путей; произвольный native/raw stdout этим механизмом не фильтруется.

Подтверждение приватности включает успешную генерацию с уникальным маркером, ошибочное имя модели и некорректный параметр генерации. Проверяется отсутствие маркера, ответа и API-токена в stdout/stderr основного контейнера, а также наличие записей о запросах.

```powershell
python -m unittest discover -s tests -v
python scripts/verify_endpoint.py --context safeboard
python scripts/check_offline_cache.py
```

Полный набор тестов, включая POSIX-блокировку и ветви downloader, запускается в Linux-образе. На Windows одиннадцать POSIX-тестов отмечаются как skipped; остальные выполняются локально. После сборки образа:

```powershell
docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges --tmpfs /tmp:rw,nosuid,nodev,size=64m -v "${PWD}:/review:ro" -w /review --entrypoint python safeboard-downloader:1.3 -m unittest discover -s tests -v
```

Тесты проверяют redirects с синтетическим токеном, выбор context, первую загрузку, cache hit без HF Hub, прерванную загрузку, повреждённый кэш и отказ без сети. Также проверяется привязка endpoint к Pod и отказ benchmark при изменении Pod или несовпадении настроек.

После исправлений от 23 октября: 48/48 тестов в Linux, на Windows 37 прошли и 11 POSIX-тестов выполняются в Linux. Реальные проверки API, приватной копии весов, офлайн-кэша и рестарта inference в том же Pod сохранены в `results/security-fixes.json`. Исторические benchmark и environment за 21 октября относятся к прежнему образу; их исходные Pod/image ID и метрики не переписывались.

Перед сдачей 23 октября выполнен новый контрольный прогон финальных образов в отдельном профиле Minikube с пустым PVC: реальная первая загрузка с SHA-256, готовность сервиса, авторизация, генерация, приватность логов, пересоздание Pod и повторная генерация с тем же PVC без скачивания. Обе сборки прошли с разрешённым Docker build cache; автоматических рестартов контейнеров во время проверок не было. Сводка — [results/final-acceptance.json](results/final-acceptance.json).

## Нагрузочное тестирование

При работающем port-forward:

```powershell
python scripts/benchmark.py --requests 8 --output-tokens 32 --kube-context safeboard --output results/benchmark.json
```

`local_config_sha256` обозначает хеш локального `serve.yaml` в UTF-8 с LF. При `--kube-context` скрипт читает фактические ConfigMap и спецификацию готового Pod, проверяет совпадение `serve.yaml`, сохраняет UID Pod, image ID, ресурсы, число рестартов и хеши конфигурации. До и после серии запрос `/v1/models` связывается с этим Pod по `X-Request-Id` в его audit log. Изменение Pod или настроек прерывает тест без записи итогового JSON. Проверяются спецификация Pod и его ConfigMap; внутренние параметры процесса vLLM отдельно не опрашиваются.

Для внешнего endpoint можно передать `--url` без `--kube-context`: измерения сохранятся с `kubernetes_evidence.status=not_collected`. Локальный файл в таком отчёте не объявляется конфигурацией сервера.

Тест использует streaming SSE, короткие и длинные синтетические промпты, параллелизм 1 и 4. Уникальные идентификаторы перед основным текстом исключают повторное использование всего длинного префикса. Перед каждым сценарием выполняется отдельный прогрев; он исключён из измерений. Выход фиксирован в 32 токена через `ignore_eos`.

TTFT измеряется до первого непустого текстового SSE-фрагмента на клиенте. Latency включает весь ответ. Throughput считается как сумма выходных токенов, делённая на полное время серии; дополнительно сохраняются запросы в секунду. p95 рассчитывается методом ближайшего ранга. Небольшая выборка предназначена для воспроизводимой локальной проверки и сравнения настроек.

Реальные измерения 21 октября 2026 года: по 8 запросов в каждом сценарии, выход по 32 токена. В колонках задержек указаны среднее / p95, в секундах.

| Промпт и средний вход | Параллельность | TTFT среднее / p95, с | Latency среднее / p95, с | Выходных токенов/с |
|---|---:|---:|---:|---:|
| Короткий, 68 токенов | 1 | 1,107 / 1,122 | 3,204 / 3,229 | 9,987 |
| Короткий, 68 токенов | 4 | 1,077 / 1,103 | 3,866 / 3,909 | 32,988 |
| Длинный, 1745 токенов | 1 | 2,159 / 2,192 | 5,168 / 5,223 | 6,192 |
| Длинный, 1745 токенов | 4 | 4,417 / 8,260 | 11,304 / 15,415 | 11,177 |

Для коротких запросов параллелизм 4 повысил суммарную скорость примерно в 3,3 раза при увеличении средней полной задержки с 3,20 до 3,87 с. Для длинных запросов выигрыш в throughput составил около 1,8 раза, а средний TTFT вырос с 2,16 до 4,42 с. В этой конфигурации рост параллелизма заметно дороже по задержкам для длинного контекста.

Первичные измерения, явно обозначенный локальный хеш и подтверждение Pod сохранены в `results/benchmark.json`, `results/benchmark.md` и `results/environment.json`. Ошибок в измеряемых сериях не было. Это небольшая локальная выборка; p95 не следует переносить на производственную нагрузку без более длинного теста.

Дополнительные пробы с выходом 128/256 токенов и разными настройками CPU сохранены в [results/performance/README.md](results/performance/README.md). По решению пользователя рабочая конфигурация оставлена исходной: BF16, OMP/MKL 8, `nobind`; эксперименты с ускорением остановлены, AWQ и AMD Zen backend не используются.

Для большого потока коротких запросов стоит экспериментально увеличивать `max-num-seqs` и бюджет `max-num-batched-tokens`, чтобы эффективнее объединять запросы, а также сравнивать число OpenMP-потоков с учётом CPU-квоты. Рост параллелизма может повысить суммарный throughput и одновременно увеличить задержку отдельного запроса.

Для длинных контекстов существенны память KV-кэша, бюджет prefill и `enable-chunked-prefill`. Бюджет батча нужно увеличивать с контролем памяти и TTFT; число одновременно активных длинных запросов — ограничивать. Prefix caching полезен при совпадающих префиксах. Эти изменения проверяются измерениями на одинаковых входах и ресурсах; текущие настройки являются исходной конфигурацией, а не доказанным оптимумом.

## Управление

```powershell
kubectl --context safeboard -n safeboard-llm get pods,pvc
kubectl --context safeboard -n safeboard-llm top pods
kubectl --context safeboard -n safeboard-llm logs deployment/vllm -c download-model
kubectl --context safeboard -n safeboard-llm logs deployment/vllm -c inference
minikube stop -p safeboard
```

`stop` сохраняет модель и состояние кластера. Удаление PVC, namespace или самого профиля Minikube удаляет локальное хранилище.
